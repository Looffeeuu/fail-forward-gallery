# Fail Forward Gallery V0.2：账户、匿名身份与内容归属

V0.2 开始把静态原型迁移为可连接正式服务的产品。当前阶段已经建立中国区手机号认证、私密会话、服务端投稿、“我的故事”内容归属，以及受角色权限保护的人工审核闭环，不使用浏览器本地存储伪造登录、正式投稿或审核决定。

## 本阶段已经开始的内容

- 新增中国大陆手机号和六位短信验证码界面。
- 新增 `auth.js`，定义可替换的认证适配器、会话状态和权限判断。
- 新增 `auth-http-adapter.js`，实现同源 Cookie 会话、请求超时、CSRF 请求头和安全错误映射。
- 新增 Node.js 本地认证服务、SQLite 账户指纹和会话存储。
- 开发验证码只输出到服务端终端，不返回给网页，不发送真实短信。
- 手机号不以明文写入账户数据库；公开 API 也不返回账户 ID 或手机号。
- 新增不包含密钥的 `runtime-config.js`；静态模式不连接认证 API，Node 服务模式会动态启用。
- 新增 OpenAPI 契约，后端可以按同一接口独立实现。
- 新增不包含账户或内容数据的 `/api/v1/health` 健康检查，便于后续部署平台判断服务是否存活。
- 新增无密钥的 `.env.example` 作为环境变量参考；服务不会自动加载该文件。
- 将私密账户身份与公开匿名身份分开。
- 新增“我的故事”工作区入口，预留投稿、审核、Follow-up、申诉和撤回状态。
- 新增登录后投稿 API；账户归属只由服务端会话决定，浏览器传入的账户 ID 会被忽略。
- 新增故事、标签和审核记录表；新投稿默认进入“待人工审核”，不会直接进入公共归档。
- “我的故事”只返回当前账户的投稿与审核状态，不返回手机号或服务端账户 ID。
- 新增审核员角色、私密审核队列、批准/拒绝理由和不可变审核事件记录。
- 只有人工批准的故事会进入公开故事 API 与 Story Archive；待审核和拒绝内容保持私密。
- 作者可以在“我的故事”查看人工决定与审核理由，但看不到审核员身份。
- 新增登录后评论：回应类型由作者选择的回应偏好决定，“不接收评论”的故事在服务端直接拒绝；评论人工批准后才会匿名公开。
- 验证码防滥用：同一手机号 60 秒内只能请求一次、每小时最多 5 次、每天最多 10 次，不论请求来自哪个网络；同一网络地址 10 分钟内最多 20 次。这些计数目前保存在单个服务进程的内存中，重启会清空；部署多实例前需要改为共享存储（如 Redis）。
- 按账户限流（`server/submission-limits.mjs`）：投稿每小时最多 3 篇、同时最多 3 篇待审核；Follow-up 每小时最多 3 条（含仅自己可见的）、同时最多 3 条待审核；评论 10 分钟内最多 5 条、同时最多 10 条待审核，且同一故事不能重复发送相同内容。计数基于数据库记录，重启服务或撤回内容都不会重置。
- 新增原作者 Follow-up：只有故事作者本人可以添加，可选“匿名公开”或“仅自己可见”；匿名公开的更新需要人工批准，仅自己可见的更新不进入审核队列或公共接口。
- 审核队列统一处理故事、评论和 Follow-up，按提交时间排序，并为评论提供被回应故事的上下文；三类内容共用同一套审核记录与审计事件。
- “我的故事”显示每篇故事的 Follow-up 状态，以及自己写过的评论和审核理由。
- 作者可以随时撤回自己的故事、评论或 Follow-up（待审核、已公开、被拒绝或私密均可），撤回立即生效并从公开页面和审核队列中移除；记录与审计事件保留。故事撤回后，其下待审核的回应与后续也会离开审核队列。
- 被拒绝的内容可以就每个审核决定申诉一次：选择结构化理由（误解语境、无可识别信息、符合规范、其他）并填写说明。任何审核员都可以复核，原审核员处理时界面会提示尽量交给他人；“撤销原决定”会立即公开内容，“维持原决定”保持私密，两种结果的理由都会显示给作者。
- 内容举报：登录用户可以举报他人公开的故事、回应或 Follow-up（每条一次，每小时最多 10 次，不能举报自己的内容）。理由包括泄露个人信息、攻击或骚扰、鼓励伤害、广告灌水、不符合作者选择的回应方式、作者可能处于危险中和其他。审核队列按内容合并举报、不显示举报人，“作者可能处于危险中”优先排列。“移除内容”按未通过审核处理，作者可以申诉；作者和举报人都会收到通知。
- 申诉以审核决定为单位：举报移除是一个新的决定，即使内容以前申诉过，也可以再申诉一次。
- 故事榜单：“正在受到关注”（近 3 天去重阅读与已通过回应，每 24 小时权重减半，回应权重为阅读的 3 倍）、“阅读最多”（24 小时 / 7 天去重阅读）、“讨论最多”（已通过回应，不含“不接收评论”的故事）和“审核团队推荐”（审核员在故事详情中推荐并公开推荐理由）。榜单每分钟更新一次，只公开排名顺序；作者在“我的故事”中私下看到自己故事的累计读者、近 7 天读者和公开回应数。只有当前公开的故事可以上榜。
- 阅读统计：同一人每天对同一故事只计一次，作者本人、疑似爬虫和同一网络来源的大量新访问不计入。未登录读者以随机的 `ffg_visitor` Cookie 区分；入库前与服务器密钥和日期一起哈希，无法跨天关联同一个人；原始 IP 只在内存中用于限流，不写入数据库。逐条阅读记录保留 8 天，之后只保留每篇故事的累计数。
- 安全保留：审核员可以把待审核的故事、回应或 Follow-up，以及因“作者可能处于危险中”被举报的已公开内容转入安全保留。内容不公开，但不算违规，不出现“未通过”或申诉入口；作者看到“暂缓公开 · 关怀优先”和关怀说明，审核员写的保留说明只在审核团队内可见。保留内容会一直留在审核队列中，直到审核员“解除保留并发布”或“转为不予发布”（后者成为普通拒绝，作者可以申诉）。
- 危险信号提示：`server/risk-signals.mjs` 用关键词识别可能涉及自伤、轻生或伤害他人的内容。命中的内容在审核队列置顶并标红，作者提交后立即看到关怀信息；仅自己可见的 Follow-up 也会显示关怀信息，但不会进入审核队列。关键词只用于提醒，从不自动拒绝、隐藏或改写内容，也会误报；试点前应请心理健康专业人员审阅这份清单。
- 求助资源：`care-resources.js` 是由团队核实后填写的求助资源清单，每条需记录核实人和日期。清单为空时只显示通用关怀文字和 120 / 110 急救报警电话，系统不会编造热线信息。
- 审核员不能审核自己写的内容：自己的故事、回应、Follow-up 以及针对它们的申诉、举报和安全保留，都不会出现在自己的审核队列里，直接操作会被拒绝，需要由其他审核员处理；审核员也不能推荐自己的故事上榜。只有一位审核员时，他自己的投稿需要等第二位审核员加入后才能处理。
- 团队管理：管理员在“团队管理”页面输入手机号、名称和角色来任命审核员或管理员；对方无需事先登录，第一次用该手机号登录就拥有权限。调整或撤销权限立即生效，对方已打开的页面也会失去审核入口。每次变更都会记录操作人和时间。管理员不能修改自己的角色（包括在任命表单中输入自己的号码），因此系统始终至少保留一位管理员。手机号只用于计算账户指纹，不保存也不显示；团队成员以管理员填写的名称显示。
- 隐私说明与社区规则：两份带版本号的文档写在 `policies.json`，网页（含静态原型）和服务器共用。获取验证码和登录前必须勾选同意当前版本的《隐私说明》，未同意时不会发送手机号；第一次投稿前会看到“动笔之前”，勾选“我已阅读并知晓”后才显示投稿表单，服务器也会拒绝未确认当前社区规则的投稿。系统记录每个账户同意的版本和时间；修改 `policies.json` 中的版本号后，所有人都需要重新确认（隐私说明在“我的账户”中重新确认）。两份文档目前是草案，标有【待团队补充】的内容（紧急情况下是否联系外部机构、审核记录保留期限、删除账户和导出数据的联系方式）需要团队定稿，正式试点前应请专业人士审阅。
- 个人数据导出与账户删除：在“我的账户”中可以下载 JSON 格式的个人数据（同意记录、内容、审核状态、申诉、举报和通知，不含手机号和内部账户 ID），也可以删除账户。删除时由用户选择已公开内容是全部删除，还是保留为属于占位账户（无法登录）的匿名内容；未公开的内容、申诉和举报说明一律删除，审核决定与理由保留但不再关联任何账户。整个删除在一个事务中完成，并结束登录。审核团队成员需先由管理员撤销角色。
- 站内审核通知：内容通过、被拒绝或申诉复核后，作者会收到通知，导航栏显示未读数量，登录期间每分钟刷新一次。通知只写明内容类型、所属故事和结果，审核理由仍在“我的故事”中查看。邮件通知待正式部署后接入。
- 同时打开多个标签页时，CSRF 令牌被另一个标签页轮换后，写操作会自动获取新令牌并重试一次，不再要求刷新页面。
- 已有的 V0.2 本地数据库在启动时自动迁移，原有故事与审核记录保持不变。
- AI 安全筛查和审核邮件尚未接入，界面会如实显示这一限制。
- 保持纯 HTML、CSS 和原生 JavaScript；暂不绑定具体云厂商。

## 试点前安全审查（2026-10-20）

已修复：格式错误的 Cookie 或请求地址会让服务进程崩溃（已复现并加回归测试）；投稿和 Follow-up 缺少频率限制；审核员可以审核自己的内容；同一手机号的验证码缺少每小时和每天上限；两处辅助函数输出未转义；静态托管缺少内容安全策略（已在 `index.html` 中以 meta 标签补充）；《隐私说明》对手机号指纹的表述不够准确。

部署时需要处理：
- 经反向代理部署后，按 IP 的限流需改为读取可信代理传入的真实地址，否则所有用户会被当成同一来源。
- 验证码、IP 限流和浏览量来源限流保存在进程内存中；多实例部署需改为共享存储。
- 服务器密钥（`FFG_AUTH_SECRET`）必须与数据库及其备份分开保存；数据库文件应只允许服务账户读取。

## 当前限制

直接使用静态服务器时，`runtime-config.js` 中的 `auth.enabled` 仍为 `false`，投稿继续使用浏览器本地原型数据。使用 `node server/index.mjs` 启动时，服务端会动态启用认证、内容与审核 API；登录后的投稿写入 SQLite，先保持私密，人工批准后才进入公共故事接口和 Story Archive。开发短信与开发审核员引导不适合生产环境；生产启动必须配置服务端密钥并使用经过审核的短信适配器。接口细节见 [账户、内容与审核 API 契约](./auth-api.yaml)。

## 本地运行

需要 Node.js 24 或更高版本：

```bash
npm start
```

打开 `http://127.0.0.1:4173`。输入手机号并获取验证码后，从启动服务的终端读取带有“开发短信 / DEV SMS”标记的六位验证码。原生 WSL/Linux Node 会把账户和会话数据库写入被 Git 忽略的 `.data/`；Windows Node 通过 WSL 共享路径运行时会改用系统临时目录，避免 SQLite 网络路径锁定问题。

`.env.example` 只说明可用变量，不会被服务自动读取，也不得填写或提交真实密钥。启动平台应通过进程环境或密钥管理功能提供生产配置。服务启动后可以访问 `GET /api/v1/health` 执行不含用户数据的存活检查。

本地验收审核闭环时，可在启动前指定一个测试手机号作为开发审核员（不要使用真实个人手机号）：

```bash
FFG_DEV_MODERATOR_PHONE=13900139000 npm start
```

用普通测试手机号投稿，再用上述审核员手机号登录，导航中会出现“审核队列”。故事通过后，可以用另一个测试手机号发表评论，再用作者账号在故事详情中添加 Follow-up，它们同样会进入审核队列。`FFG_DEV_MODERATOR_PHONE` 只用于本地开发；生产模式检测到该变量会直接拒绝启动。

第一位管理员需要由能登录服务器的人用命令行设置，之后的审核员和管理员都在网页“团队管理”中任命：

```bash
npm run staff -- grant-admin 13800138000 项目负责人
```

`npm run staff -- list` 可以查看当前团队。命令行同样只保存手机号指纹；手机号会留在命令行历史中，请在可信的服务器环境中执行。
